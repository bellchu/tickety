# Persisted settings secret encryption

Tickety encrypts every sensitive value written to the `settings` table with
AES-256-GCM. Browser/API masking is not a substitute for this at-rest control.
The database stores a versioned ciphertext envelope with a key identifier;
the key material remains deployment-owned and is never stored in Tickety or in
Helm values.

## Deployment contract

Inject both variables into every API, worker, migration, and recovery process
that can read or write the database, including Docker Compose and MicroK8s
development migration Jobs:

```dotenv
TICKETY_SETTINGS_ENCRYPTION_ACTIVE_KID=2026-q3
TICKETY_SETTINGS_ENCRYPTION_KEYS_JSON={"2026-q3":"<base64-encoded-32-byte-key>"}
```

`TICKETY_SETTINGS_ENCRYPTION_KEYS_JSON` is a JSON object whose values are
standard-base64 encodings of exactly 32 random bytes. Generate, store, and
distribute those values through the approved secret manager. Do not put them
in `.env.example`, Git, database rows, backups, or Helm values files.

For Helm, the recommended contract is an externally managed `existingSecret`
containing `DATABASE_URL`, `TICKETY_SETTINGS_ENCRYPTION_ACTIVE_KID`, and
`TICKETY_SETTINGS_ENCRYPTION_KEYS_JSON` (plus `POSTGRES_PASSWORD` when using
the bundled database). Helm cannot read an external Secret's data during a
portable render, so it documents that required key set and the migration Job
enforces it before schema changes. If the chart manages its own Secret instead,
its template rejects a render unless both settings-encryption keys are supplied
in the runtime `secrets` input. Use that only from an uncommitted secret source;
production key material belongs in an external secret manager.

`config.extra` is rendered into a Kubernetes ConfigMap, never a Secret. The
chart rejects settings-encryption names and credential-like extra keys at both
schema and template validation, so a missing external Secret cannot be worked
around by placing key material in a ConfigMap or Helm release history.

No key is generated by the application. A missing, malformed, unknown, or
tampered key/ciphertext fails closed. A legacy plaintext sensitive setting
also fails closed instead of being silently read.

## First migration and rotation

Take and verify an encrypted database backup before changing keys. To migrate
known legacy plaintext settings, inject a new keyring and run the explicit
operator action from a trusted one-off maintenance environment:

```sh
APP_MODE=production DATABASE_URL='...' \
TICKETY_SETTINGS_ENCRYPTION_ACTIVE_KID=2026-q3 \
TICKETY_SETTINGS_ENCRYPTION_KEYS_JSON='{"2026-q3":"..."}' \
PYTHONPATH=. .venv/bin/python scripts/reencrypt-settings-secrets.py \
  --allow-legacy-plaintext --from-kid=2026-q3
```

`--from-kid` is also required for this first plaintext adoption when the
database already has sensitive rows but no durable fence. Here it repeats the
new active KID: it is an explicit fence-bootstrap assertion, not a claim that
the legacy plaintext had a KID.

For rotation, first deploy this fence-aware release through `./deploy.sh
kubernetes` while retaining the **old** active KID. Before changing that active
KID, run a trusted one-off bootstrap with the old keyring and an explicit
confirmation; this creates the durable, non-secret active-KID fence even when
no runtime process has written a sensitive setting since the fence-aware
release was deployed:

```sh
APP_MODE=production DATABASE_URL='...' \
TICKETY_SETTINGS_ENCRYPTION_ACTIVE_KID=2026-q3 \
TICKETY_SETTINGS_ENCRYPTION_KEYS_JSON='{"2026-q3":"..."}' \
PYTHONPATH=. .venv/bin/python scripts/reencrypt-settings-secrets.py --from-kid=2026-q3
```

Then use a trusted one-off environment with both KIDs, make the **new** KID
active, and explicitly confirm the same durable old KID:

```sh
APP_MODE=production DATABASE_URL='...' \
TICKETY_SETTINGS_ENCRYPTION_ACTIVE_KID=2026-q4 \
TICKETY_SETTINGS_ENCRYPTION_KEYS_JSON='{"2026-q3":"...","2026-q4":"..."}' \
PYTHONPATH=. .venv/bin/python scripts/reencrypt-settings-secrets.py --from-kid=2026-q3
```

`--from-kid` is mandatory when the durable fence differs from the local active
KID, and when adopting existing sensitive settings without a fence. It prevents
two operators from silently rotating over one another. The rotation transaction
holds the fence while it authenticates and re-encrypts every sensitive row:
PostgreSQL takes a row lock and SQLite uses a sentinel write lock. A stale
process may continue serving ordinary traffic during this brief operation, but
its later sensitive write (for example an OAuth token refresh) fails closed
instead of persisting the retired KID.

After the one-off command succeeds, run `./deploy.sh kubernetes` again so it
drains old database writers and rolls every API/worker Pod with the new active
KID. Verify the migration preflight and recovery from a backup, then retire the
old KID. Loss of every historical KID makes prior ciphertext intentionally
unrecoverable; restore the matching keyring before restoring an older backup.

The command reports counts only, never values. It is transactional: an
authentication or configuration failure rolls back all changed rows.

## Helm upgrade gate

Every migration entry point (Helm, Docker Compose, and MicroK8s development)
first runs a read-only settings-encryption preflight, then runs `alembic upgrade
head`. It validates the deployment keyring even for an empty database and
authenticates every persisted sensitive setting without the application's
availability fallback. A missing `settings` table is permitted only when the
database has no tables at all, so the first Alembic run can create an empty
schema. Any initialized, partial, or unrelated-populated database missing
`settings` fails closed. The gate also stops before schema migration on
legacy plaintext, an unknown KID, malformed ciphertext, a missing keyring, an
unfenced ciphertext whose KID differs from the deployment active KID, a
mismatched durable fence, or a database/table/query error. It never prints a
setting value or key material.

For an installation created before this control, complete the explicit
plaintext migration above from a trusted one-off maintenance environment using
the **new release image** and the same deployment Secret. Verify its count-only
success output, then run `./deploy.sh kubernetes`. Do not bypass the failed
migration Job, remove the preflight, or roll out the new API/worker image until
the preflight passes. This preserves the previous healthy release while the
operator performs a visible, backed-up data transition.
